# 回答原句联动剪辑

用户当前方向是通用长视频理解及对应片段切分。已有助手回答能引用原句，但“送到剪辑要求”只传文字，后续独立检索可能选到视频中另一处相似表达。本轮将明确选择的回答原句冻结到独立剪辑请求，让理解与剪辑使用同一处证据。

## 用户流程

在成功的视频证据回答中选择一条或多条引用，点击“按所选原句剪辑”，将原问题、剪辑要求与原句预填到剪辑面板。已有未保存内容或未决提交继续拦截覆盖。预填不发模型请求，用户提交后才建立独立请求和预算。

首版每次选择对应一个剪辑目标，可由多个有序区间组成。模型可以扩展前后解释，候选必须完整保留所选原句。相同术语在别处出现，不能代替用户所选位置。普通文字剪辑保留原来的多目标流程；用户可在提交前明确移除锚定，继续普通查找。

候选仍需人工回看、保存、确认及导出。ASR 句级时间不等同于词级定位；无法安全剔除句内引导或无法组成解释时，保留 NEEDS_REVIEW / NOT_FOUND，不自动升级为 FOUND。“保留完整解释”是规划要求，不能由整句覆盖检查证明语义完整。

## 冻结身份与共同契约

`POST /api/jobs/{jobId}/clip-requests` 新增可选字段：

```json
{
  "instruction": "围绕所选原句剪出缓存失效原因，保留解释",
  "max_text_calls": 4,
  "source_answer": {
    "turn_id": "00000000-0000-0000-0000-000000000001",
    "utterance_ids": ["c_001_u000002", "c_001_u000003"]
  }
}
```

浏览器只提交 turn ID 与原句 ID，不提交可信时间或原文。Java 从同任务的成功 VIDEO 会话/轮次解析原始结果，重新校验回答来源、工具实际观察证据、摘要及选中原句。CAPTION、GENERAL、INSUFFICIENT、失败或别的视频回答不能作为锚点。选择必须唯一、按原视频顺序，1～24 句，选中原文合计不超过 12000 UTF-16 单元。

V18 只为 `clip_request` 增加可空的冻结 JSON 与摘要列，不修改原回答、话题、审核、字幕或导出。公开 `source_answer` 为 null 或 [answer-source.schema.json](../contracts/answer-source.schema.json)；私有 claim 的 `clip_request.answer_source` 下发同一对象。`answer_hash` 是原完整已验证回答结果的 canonical JSON SHA-256，冻结对象另有服务端摘要。私有来源同时保留完整已验证回答结果，后续可重算摘要和原引用，不依赖一段不可复算的 hash 字符串；它不公开、不进入模型 claim。

上下文包含全部所选原句，并在总原文不超过 12000 UTF-16 单元时加入每句前后各一条完整邻句，按来源顺序排列，不截断一句。它是有限局部上下文，不能声称看过整段视频。Schema 检查结构；Java/Python 还检查 UTF-16 总量、视频/转写身份、ID 顺序、上下文计算、原文及毫秒映射。

## 执行与候选约束

有锚请求使用独立 `ANCHOR_CLIP` 阶段、`CLIP_REQUEST` owner 和 `TEXT` 资源。只有显式声明新能力的 Worker 可领取；旧 `SEGMENT` Worker 继续处理普通请求。新阶段复用幂等领取、心跳、租约、attempt/run_token、持久调用预算、有限重试和 UNKNOWN 语义，不新增 ASR。

Python 用已校验 ASR 再核对冻结对象，将所选发生位置及邻句加入规划输入，模型只选择 ASR ID。此处直接按冻结原句 ID 取局部上下文，不重新执行全局 BM25 或向量检索，`retrieval_mode=anchor_context`；索引摘要绑定原来源、回答摘要和具体上下文。输出沿用 clip-plan v1.0，但 `provenance.prompt_version=anchor-clips-v1`；普通请求仍为 `intent-clips-v1` 与原检索模式，身份和缓存不能混用。模型不能通过返回另一处相似句来满足约束。

锚定方案只能有一个 goal/output。FOUND 或非空 NEEDS_REVIEW 的 parts 必须完整覆盖全部所选原句，并且不能将锚句列为 excluded；NOT_FOUND、空 NEEDS_REVIEW 允许诚实无候选且不能启用。自动候选的区间和排除项只能来自冻结局部上下文，不能将未展示的中间句夹进候选。人工可用完整 ASR 向前后拓展，但仍必须保留锚句及原自动分类。Java 在接收、保存、读取自动基线、确认和创建导出时重查这一约束，人工编辑也不能静默删除锚句。所有输出初始不勾选，只有 FOUND 可人工选中。

## 页面与恢复

面板显示对应回答、选中原文与原视频时间；本机备份与文件导入必须保留锚定身份。恢复前只读获取原轮次并重新核对来源、成功状态、原句和回答身份；核对失败时只读下载，不退回普通文字剪辑。旧无锚草稿保持兼容。

提交结果未知时保留原幂等键及含锚句的原始输入指纹，不换键重发，不清预算；resume 创建新轮次但保留冻结锚定来源。服务端快照、合并、保存回执和导出继续使用原来源及 revision/hash 校验。

执行器页面同时接受完整旧 5 阶段、字幕校对 6 阶段与新增锚定 7 阶段快照；支持某能力的执行器必须有相应队列状态，不能过滤未知阶段后误报可用。

锚定新建、未知提交原键核对及锚定 resume 在 POST 前先 fresh 读取 `/api/executors?job_id=...`，严格解析且确认 `ANCHOR_CLIP` 队列存在。此处核对服务器协议，不要求在线 Worker；读取失败、畸形或旧五/六阶段服务都不发写请求，保留原锚和回执。避免新前端向旧单实例后端提交时，旧 JSON 绑定器忽略新字段并创建普通 SEGMENT。部署仍须保持同一路由的一致后端版本，不把一次能力快照当作负载均衡后任意节点的版本保证。

升级顺序为先部署支持 V18 的 Java，再更新 Worker 并声明 ANCHOR_CLIP 能力，最后使用新入口；普通旧 Worker 可继续处理 SEGMENT。仅前端 HMR 更新不代表服务端已经可用，不通过清注册、放宽能力或旧阶段代领来掩盖版本差异。

## 验收边界

重点反例是同一术语在两处出现：只选第二处回答引用时，第一处不能冒充候选。另覆盖跨视频/旧来源、非 VIDEO、篡改原文时间、乱序或超限、部分毫秒重叠、排除锚句、人工修订绕过、取消、重试、预算以及旧协议兼容。

真实供应商与浏览器结果在完成后追加。合成测试不证明语义准确率、长视频全量理解或真实付费意愿，不能把工程约束写成已测业务收益。
