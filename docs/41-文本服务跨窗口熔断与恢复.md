# 文本服务跨窗口熔断与恢复

2026-11-06：在已有单请求有限恢复上，补充同一分析阶段内的平台健康记录。适用于长视频话题窗口、格式修复和按需剪辑中不同的逻辑文本请求。

## 解决的问题

单个逻辑请求已有 3 次尝试、单次 90 秒和总窗口 240 秒的限制。但如果主平台持续不可用，每个新窗口仍先请求主平台两次，再使用备用平台，就会重复等待相同故障。新逻辑请求应参考本阶段近期的实际服务结果，优先选择可用的平台。

## 执行约定

- 默认连续 2 次可恢复的实际网络故障后短期熔断 60 秒；认证、余额或额度错误立即熔断。成功的实际响应清除该平台的连续故障。
- 记录按阶段、服务端点、协议、模型和凭证指纹隔离。新分析代次不继承旧阶段的熔断；同一阶段换 Worker attempt 后可读取记录。文件不保存原始密钥，公开进度不增加服务地址或凭证字段。
- 首次出现的逻辑请求排除仍在冷却的平台，按原配置优先级选择其余平台。只有一个可用备用时，它仍有本逻辑请求最多 3 次尝试的空间。所有平台均在冷却时，选择最早可恢复的一个平台做有界尝试，仍受原账本、次数和时间限制。
- 冷却到期的平台重新参与选择；失败的恢复探测在有备用时尽早切换，避免再次完整等待两轮。探测标记与路线一起冻结。
- 只有实际外发后的服务响应或网络异常更新健康信息。旧响应重放、旧 UNKNOWN、Java 账本错误、取消、租约失效和存储错误不重复累计平台故障，较早成功响应的重放也不能清除较晚发生的熔断。

```mermaid
flowchart LR
    W1[窗口一] --> P1[主平台失败两次]
    P1 --> B1[备用平台成功]
    B1 --> H[本阶段主平台冷却]
    H --> W2[新窗口优先备用]
    W2 --> C[冷却到期]
    C --> P2[允许主平台恢复探测]
```

## 冻结与账本

新逻辑请求使用版本 2 的冻结执行策略，保存允许的平台配置、选定顺序、探测标记及熔断参数。恢复时先读取原策略，不根据当前健康信息重新排列路线。已存在的版本 1 策略保持原身份和原路线；不会直接给旧文件追加字段并改变其 policy hash。

恢复策略引入前的旧调用可能已有账本，却没有冻结文件。首次创建策略前，先对原主平台第 0 次尝试做只读 lookup；发现已有调用时冻结版本 1 的原路线，继续按旧身份恢复。只有原调用不存在时，才按健康信息创建新路线。这个兼容检查不会预留次数或外发模型请求，账本不可用时也不能假装“没有旧结果”。

主平台第 0 次尝试保留历史调用身份。直接从备用平台开始的第 0 次尝试绑定原逻辑请求和冻结策略，避免不同原请求在备用协议重编码后变成相同请求体、错误合并账本。后续尝试仍使用独立序号，UNKNOWN 不重发、不改写；新调用独立预留并计入原次数上限。

健康记录是选路建议，缺失、损坏或不可读写时可回到原有限恢复逻辑，不能重置已冻结的请求策略、原次数或预算。冻结执行策略仍必须可靠持久化，损坏或配置不匹配时明确失败。已经成功的响应经过原哈希验证后继续重放，恢复窗口过期也不新增调用。

本轮不扩展为跨任务全局熔断，不主动发送探测请求，不增加备用平台或购买模型额度。没有有效备用配置的旧任务仍遵循其允许的模型名单。

## 验证记录

本地 Python 全量 **1206 项和 98 项 subtests** 通过，Ruff 与 diff 检查通过。随后仅新增一个双备用测试，独立黑盒文件共 9 项全部通过：主平台和第一备用认证失败后，下一窗口直接使用第二备用，三平台鉴权相互隔离。其中旧成功账本没有冻结文件的用例先复现了多余调用，再验证修复后账本与外发次数保持不变。其余覆盖平台连续失败、认证/额度、HTTP 200 空或非 JSON 响应、重放不更新健康、阶段及凭证隔离、预算/时间、原子冻结、链接、损坏与只读存储。

使用两个明确标记为合成服务的本地 HTTP Server，经过真实 HTTP 传输和 BudgetTransport 验证：第一窗口主平台失败两次后备用成功；换 Worker attempt 后第二窗口直接备用；冷却到期的主平台探测失败后立即切备用；之后主平台恢复成功。整个用例累计 8 次文本外发、0 次 ASR。8 次预算用满并将恢复窗口时间推进到过期后，仍能只读重放第一窗口结果，账本和外发数不增加。生产默认 60 秒冷却通过受控时钟推进验证，没有用该测试推导真实耗时。

本轮没有调用真实模型、没有新增 ASR，也没有改写已有用户分析结果。跨平台故障由明确的合成服务验证，不声称真实平台发生故障，也不据此推导准确率、生产延迟或成本下降。公开检查结果以本轮提交的 GitHub CI 为准。
