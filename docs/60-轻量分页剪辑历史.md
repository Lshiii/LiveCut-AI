# 轻量分页剪辑历史

旧历史列表最多一次读取 100 个完整请求，每项带整份 ASR、最新方案和引用来源，并分别查询阶段、方案和确认版本。长视频反复尝试剪辑时，历史数量会放大传输、JSON 解析与数据库查询。上一轮已在隐藏时暂停轮询，本轮将历史元数据与可编辑详情分开。

## 用户行为

历史面板分页显示请求要求、状态、时间、预算和类型。翻页或回到最新仅浏览历史，不切换当前编辑文档，也不覆盖未保存内容；点击具体请求后，读取并验证完整详情，才进入原审核与导出流程。当前请求不在所看历史页时仍保留编辑器及选择。

新请求、保存回执及草稿恢复继续依赖完整来源与版本校验。列表显示的“原句引用”只是来源类型提示，不能充当回答证据、方案确认、模型权限或导出许可。

## 只读接口

新增 `GET /api/jobs/{jobId}/clip-request-history?limit=20&cursor=...`，原完整列表接口保留。默认 20 条，limit 为 1～30 的整数；无 cursor 表示最新页。公共结构见 [clip-request-history.schema.json](../contracts/clip-request-history.schema.json)。

页面包含 `schema_version=1.0`、job_id、items、limit、next_cursor 和 active_count。每条元数据只包含请求/任务/视频 ID、原要求、状态、state_version、创建/更新时间、预算、来源摘要与时长、revision、plan_hash 和 source_mode，不返回转写、方案正文、引用原文或完整回答。列表不是完整详情或来源校验凭证。

next_cursor 为不透明的有界 base64url 字符串，前端原样回传，不解析或据此授予权限。服务器严格检查版本、同任务、边界 ID 与数据库微秒时间；边界必须真实属于本任务且排序关系合法。无效 limit 返回 `400 INVALID_CLIP_HISTORY_LIMIT`，无效 cursor 返回 `400 INVALID_CLIP_HISTORY_CURSOR`，不存在任务返回 `404 JOB_NOT_FOUND`。

## 分页与一致性

按不可变 `(created_at, id)` 倒序 keyset 查询，多读一条判断下一页。首屏固定当时最高位置作为 ceiling；下一页限制在 ceiling 以内且严格早于上页末尾。较新的 tuple 不会挤入旧页，修订、状态和预算变化不改变排序。返回最新页会重新建立边界。

ceiling 是游标范围上界，不是跨 HTTP 请求持有的数据库 MVCC 快照。若记录晚提交或被回填较早 created_at，落在未读范围内的 tuple 仍可能出现于后页；已越过的 tuple 不会因 offset 位移再次出现。需要发现已读范围内的新记录时返回最新，不能宣传冻结了全部历史成员集合。

私有 cursor 的时间精确到数据库 DATETIME(6)，ID 使用数据库 ascii_bin 一致的字符串顺序，不使用 UUID 有符号高位比较。公开 Instant 可能含微秒，前端保留小数精度比较，不能只用会截断微秒的 Date.parse 来验证同毫秒记录的顺序。

页面和 active_count 在同一只读一致性快照读取，不持有业务 FOR UPDATE 行锁。active_count 反映整个任务当前 QUEUED/RUNNING 请求总数，不限当前页或 ceiling，供 5 秒/60 秒刷新策略判断。页查询复用既有 `(job_id,created_at,id)` 索引；不为每个列表项构造 Snapshot 或查询详情。

查询条数有界不等于数据库扫描行数只与页大小有关；尤其全任务 active_count 需要独立核对索引与执行计划。本轮重点验证响应和 JSON 解析不随完整 ASR/方案正文放大，不直接宣称吞吐量、总耗时或成本提升。

## 前端与旧服务

历史元数据、当前分页游标和已验证完整详情分别存储。新接口的详情缓存只接收通过完整解析的详情 GET 或真实写回执；metadata 不得传给 accept/newestIntentSnapshot，不得用于认领未知保存、放弃本地稿或恢复版本。需要最新可编辑基线时，仍读取完整详情。

翻页具有独立读取生命周期，迟到页面不能替换新任务/新页，不改变 selectedId 或写回执代次。切换请求仍遵守原草稿、字幕、范围选择器和 pending 守卫。后台轮询继续遵守 [刷新生命周期](./59-按需剪辑刷新与前台恢复.md)，当前页元数据与当前选中详情独立核对。

只有新端点实际 HTTP 404 才启用本页旧服务兼容：严格解析旧完整列表，再分页显示。经过同样严格完整解析的旧列表项仍可作为原有完整快照缓存，保留旧服务在详情暂不可读时的保存回执/明确放弃核对能力；这不允许把新摘要强转成完整快照。网络故障、5xx 和畸形成功响应不退回大列表或清已有好数据。兼容能力缓存避免每 5 秒重复探测；手动刷新/聚焦可核对服务升级，已看的旧页与编辑稿保留，由用户回到最新切换新分页。旧服务仍有原完整列表载荷与最近 100 条上限，兼容不等于已启用新后端的小响应。

路由能力与有效活动样本独立：探测失败或只确认旧路由存在时，不清上次有效活动数。只有整份旧列表解析、同源版本缓存合并全部成功，才原子采用最近 100 条的已知活动数；它不是全任务计数。当前选中的完整详情和未完成导出始终独立参与快速刷新判断。

## 验证要求

覆盖同时间及同毫秒不同微秒记录、UUID 高位排序、分页时并发插入、状态/修订变化、不重排不重复、跨任务/失效/超长 cursor、坏 limit、空列表，以及响应不包含大对象。

使用隔离合成数据验证短/长 ASR 与方案正文扩大时轻量响应字节和查询条数；合成场景单独标记，不写成真实长视频语义或性能效果。真实只读接口与浏览器另行核对分页、选中详情、草稿/回执保留、旧服务404兼容及错误不降级，不调用新模型或 ASR。
