# 待核对候选人工选用

## 用户问题与流程

已有 NEEDS_REVIEW 候选允许改标题和原句区间，但普通保存、确认及导出始终禁止选中。真实旧请求中存在这样的目标：部分解决步骤与关注引导混在同一 ASR 句，用户可以选择保留当前整句或调整为其他完整句，但不能据此把 AI 判断改写成 FOUND。

新增独立的“人工核对并选用”：先调整方案、勾选需要的 FOUND 并保存，再一次核对本版本全部需要人工选用的 NEEDS_REVIEW。逐项目填写说明，明确接受当前句级边界及可能保留的混合内容。该动作建立新修订及不可变核对批次；之后仍需单独确认、生成 MP4。它不新增模型调用，不改变原始 ASR、r0、AI 分类、字幕确认或旧导出。

人工选用不宣称程序证明了语义完整、用户确实听完、消除了句内引导或获得了词级边界。NOT_FOUND、空 parts 或空 evidence 不可人工选用；原句锚定、原文时间、排除冲突和有序不交叠约束仍全部生效。

## 不改变自动方案

保持 clip-plan 1.0 完全不变，NEEDS_REVIEW 的 enabled 始终为 false，普通 PUT 不能写核对信息或改变分类。有效交付集合为 FOUND.enabled 与该修订人工批次中的输出。界面用独立“人工已选用 · rN”提示，不把禁用的自动复选框当作人工选择状态。

人工批次是完整替换集合，不是逐条追加。弹窗默认带入当前有效批次，明确展示全部下版所选项，避免第二次核对 B 时意外丢失 A。提交零项明确称为“清空人工选用”，也建立新版本。普通 PUT 建立的新修订不继承任何旧核对；本地编辑即提示保存后需重新核对，不能把旧授权应用到草稿。

## 接口合同

`POST /api/clip-requests/{id}/manual-reviews`，Idempotency-Key 为规范小写 UUID，也是不可变核对记录 id。请求只接受：

```json
{"base_revision":1,"plan_hash":"<64位小写SHA256>","outputs":[{"output_id":"output-002","note":"核对当前两段并接受整句边界；不主张覆盖其他未保留步骤。","accept_sentence_boundaries":true}]}
```

outputs 为 0～6 项、按已保存 plan 输出顺序、无重复；每项必须是原分类 NEEDS_REVIEW，具有合法非空 parts/evidence，note 非空且不超过 1000 UTF-16 单元，accept_sentence_boundaries 必须 true。客户端不能提交可信时间、状态、output_hash、修订或核对摘要。

服务器事务按 analysis → request 原顺序持锁，先检查该 key 的既有记录。同 owner 和原输入指纹重复提交直接返回原不可变记录，即使最新修订已变；同 key 不同输入/owner 返回 409 IDEMPOTENCY_CONFLICT。只有新 key 才核对 base_revision 为当前、plan_hash 为当前实际 canonical plan SHA；重查原 r0、源 ASR 身份、排除项与锚句。全部项目合法后，原子复制已保存 plan 到 base+1、写完整核对批次、更新请求 head/state_version。中途失败不产生部分选用。

`GET /api/clip-requests/{id}/manual-reviews/{reviewId}` 返回同一不可变记录；确实不存在返回 `404 CLIP_MANUAL_REVIEW_NOT_FOUND`，缺路由 404 不能当作业务不存在。

公共 Review 的精确字段：schema_version=1.0、id、request_id、job_id、video_id、source_hash、transcript_hash、duration_ms、automatic_plan_hash、base_revision、base_plan_hash、revision、plan_hash、outputs、created_at、review_hash。每项 outputs 精确为 output_id、goal_id、output_hash、note、accept_sentence_boundaries。revision=base_revision+1；复制方案使 base_plan_hash=plan_hash。output_hash 是当前完整 output 的 canonical SHA，含原分类、false enabled、区间、排除项、证据、标题与说明。review_hash 是除自身外完整 Review 的 canonical SHA，含固定 id 与 UTC 微秒 created_at；读取不重新生成时间或摘要。

完整 Snapshot 新增 manual_review:null|Review，仅返回当前修订的批次。新 Java 显式输出该键；缺键兼容旧服务阅读，但不表示旧服务支持人工选用。人工新建前必须 fresh GET 完整 Snapshot 并确认新字段存在，不能静默降级到普通 PUT。摘要历史接口保持原合同，不承载人工授权。

确认和新建导出在存在批次时必须提交精确 manual_review_hash；缺失、错误或在无批次版本伪造该字段均拒绝。旧普通无核对修订的请求字段保持兼容。确认表新增可空 manual_review_hash，人工修订的导出必须同时匹配计划及核对摘要，不能把旧客户端未见人工集合的确认当成人工授权。确认不可悄悄重写；不匹配需明确冲突。有效 confirmed_revisions 只包含与对应核对绑定一致的确认。

## 持久化与导出

V19 新增 append-only clip_plan_manual_review：id 主键、request_id、request_hash、base_revision/base_plan_hash、revision/plan_hash、review_hash、review_json、私有 source_snapshot_hash、created_at；每 request/revision 唯一，并绑定对应 plan revision。源文档摘要绑定创建时实际核对的 frozen source_json，结合实际转写来源核验，不能只信列上的 hash 标签。历史批次与 r0 不覆盖，普通保存不复制核对批次。

clip_plan_revision 同时新增成对可空的 manual_review_id/hash 不可变标记，普通修订默认为空，人工新修订与核对行在同一事务写入。人工记录缺失、标记与记录不符或摘要错误时必须报 CLIP_MANUAL_REVIEW_INVALID，不能静默将应有证明的版本解释为普通 manual_review:null，也不能让普通保存回执误认它。

Java 创建导出时重验整份证明、实际计划、源身份和确认，将 Review 与其摘要纳入 export frozen_json 与 snapshot_hash；只有被证明明确选用的 NEEDS_REVIEW 加入 frozen clips。历史普通导出 JSON 与指纹不变。claim、完成结果、内容及字幕来源等消费链须重验新证明与冻结 clips 的绑定，篡改或缺失时拒绝读取/领取/发布。

Worker 仍只接收既有 EXPORT_CLIP 的源视频、parts、snapshot_hash 等字段，不新增 manual_review 到严格私有 claim。Python 不负责判断人的核对权限。成片字幕仍按原 parts 映射 ASR，不自动确认字幕或消除裁句复核。

## 前端回执和恢复

核对弹窗禁止在未保存修改、保存待核对、未决创建、原句选择或字幕 pending 时提交。提交前冻结 key/body、来源和 base；同浏览器多页写入或移除本机回执前重新比较 key/input，不覆盖或删除另一页。回执可以保留待核对输入，不能从备份恢复人工授权。

UNKNOWN 先 GET 已知 review id，只有明确业务不存在才允许原 key/原 body 重试；该 404 也不证明旧 POST 永远不会完成，不能换 key。通用 404、网络失败、坏响应均保留原回执。POST 成功但 fresh Snapshot 失败时显示“核对已保存，当前版本待核对”，不新增 POST。收到旧记录但 head 已更新时，只显示历史完成，不授权当前版本。

若精确原 key/body 的重试明确返回 `409 CLIP_PLAN_REVISION_CONFLICT`，不能永远卡在 UNKNOWN，也不能仅凭此前一次 404 丢弃回执。必须在这次 409 之后再 GET 同 review id，仍为业务不存在，并 fresh GET 严格核验同 owner、同源的完整 Snapshot，确认 head.revision 大于原 base_revision。服务器同锁内先查幂等键再检查单调 head，满足这些条件才可认定原操作因版本推进未落库。保留回执下载入口，让用户明确「解除原操作阻塞并采用新版」；该动作再 fresh 核对及 CAS 后只清本页原回执，不覆盖普通草稿、不生成新 key、不自动确认或导出。任何网络失败、通用 404、坏响应、来源不符或版本未推进均不满足此终态条件。

普通 PUT 的未知回执不能把同 plan_hash、不同 revision 的人工批次误认作保存成功：incoming.manual_review 必须为空才能认领普通保存。相同版本不能被迟到响应删去或更换人工批次；跨任务、卸载、隐藏及迟到 finally 沿原读取生命周期守卫。确认/导出携带 fresh 版本对应的精确摘要，人工提交不会自动触发后续操作。

## 验收

测试批量原子性、多目标集合替换/清空、同 hash 不同 revision、普通修改失效、r0 与原分类保留、NOT_FOUND/空候选/排除冲突/锚句缺失拒绝、错误摘要/跨 owner/重复幂等键/并发 base、人工核对确认与旧无证明确认隔离。覆盖 Worker 合同不变、冻结证明篡改、内容与字幕来源检查、普通保存回执误认、跨页 UNKNOWN、两个未决回执的恢复、版本推进后的显式终态出口、旧服务及迟到回执。优先复用已有真实 NEEDS_REVIEW，无新增模型或 ASR；合成测试与开发 Agent 核对不写成独立人工准确率或付费需求验证。
