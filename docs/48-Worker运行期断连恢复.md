# Worker 运行期断连恢复

目标是避免 Java 的短暂重启让计算进程永久离线、后续任务一直排队。此机制恢复执行器连接，不把未知模型结果改写成成功，也不承诺正在执行的旧阶段一定继续原计算。

## 问题来源

上轮字幕功能部署时，已确认空闲的原 Worker 在 Java 不可用后退出，自己的 stdout 最后记录为 JAVA_UNAVAILABLE，操作系统中原进程已不存在，执行器登记也变为离线。后来通过现有脚本人工启动了替代进程，原任务未变。

原实现的运行期 heartbeat 发生任何网络错误就设置共享 stop，持续执行循环随后抛出 presence 错误。已有 45 秒注册等待只处理“启动新进程与旧会话冲突”，不能证明运行中的 Worker 能熬过后端断连。

## 恢复与停止

连续运行的 Worker 增加独立 reconnect_wait_seconds，默认 180 秒，允许有限数值 0..3600，0 禁用运行期恢复。CLI 为 --reconnect-wait-seconds；PowerShell 为 -ReconnectWaitSeconds。已有注册等待 45 秒独立保留，一次性 --once 保持单次执行语义。

一轮连续不可用从首次故障起算，用单调时钟限制后续尝试；仅完成注册不足以清空故障时间，当前会话的有效 ready/claim 查询与一次真实 heartbeat 都成功，才能结束本轮恢复；不会仅因注册或空查询成功就重复延长恢复窗口。长任务不必等计算完成才解除已经验证恢复的故障窗口。认证、配置和非法协议响应不会被泛化成可无限重试的网络故障。

用户停止与会话故障分离。用户取消始终有效，不能用 stop.clear() 恢复 Worker。恢复等待期间持续持有本地 journal 独占锁，不让另一个进程抢用相同执行目录。

## 会话、旧执行与回执

- 每个会话的 heartbeat、截止、错误与停止信号互相隔离，旧响应不能延长新会话或注销新会话；旧心跳线程未结束前不建立新会话。
- 所有内部 RPC 都采用累计响应截止和取消检查，连接池等待也受剩余时间限制，不能用持续缓慢响应反复刷新读取等待。底层截止按剩余时长转换至 HTTP 客户端的单调时钟，恢复完成时对共享截止状态加锁/取快照，避免心跳并发清空产生类型错误。系统 DNS 解析仍遵循操作系统行为，无法强制取消的线程不能被假定已退出。
- 连接不确定时不领取或新派发计算；旧 LeaseGuard 失效后保持失效，FFmpeg 子进程按原机制停止并回收，不因 Java 恢复在线而复活。
- 旧不明 claim 不能以新 session 再发送原 claim ID。如果原请求从未到达 Java，这样做会真领取一个新 attempt，却在 Python 的 session 检查处失败。需要先完整保存本地审计记录，再放弃本地未明 claim；已接受的旧租约由 Java 自己回收。
- 已有 worker-result/pending-callback 优先按原内容、attempt 和 token 重放。只有 HTTP 409 的明确 fencing 拒绝才可完整归档为已拒；归档写入和 pending 删除都成功后，连续循环才允许继续。register/ready/claim 的同名错误不能冒充 callback fencing；5xx 正文里的 STALE_ATTEMPT 也不能清理回执。认证、配置或归档失败保留可核对记录，不忙循环。
- 不清理模型账本、原请求身份、checkpoint 或计费预算。ASR 无 task ID 的 UNKNOWN 不重新提交；SUBMITTED 和已有 task ID 的恢复仍走原轮询协议。没有通用供应商结算回执的场景继续明确暴露待核对/失败，不能谎报已成功恢复识别。

## 可观察性

生命周期输出区分 reconnecting、recovered、reconnect-exhausted，包含执行器标识、受控错误码、已等待时间与剩余时间。日志不输出会话 UUID、鉴权信息或地址。恢复证明需要同一个进程持续存活、它自己的生命周期事件和服务端后续 heartbeat；一张登记快照不足以证明当前替代进程已恢复。

## 验收关口

合成测试需覆盖 ready 与 heartbeat 各自断连、TTL 内外恢复、注册 ACK 丢失、其他在线会话、用户停止、非法/鉴权响应、旧 claim 的已受理/未受理两分支、原回执重放和旧心跳晚到隔离。活动媒体和 ASR 预算测试继续保留旧 guard/账本约束。

真实网络验收使用明确的 QA 执行器、已完成 TIMELINE 的只读目标和可控本地代理。生产 Java 及主 Worker 保持运行；让 QA 子进程经历超过 Java 会话 TTL 的故障后恢复，并单独检查持续故障的窗口耗尽及等待中用户停止。不得为了验证恢复而提交付费模型请求或修改旧业务结果。

运行期重连是有上限的进程内恢复，不替代部署环境的进程管理；超出窗口会带原因退出，不能宣传为无限可用或所有任务自动成功。


## 2026-11-07 验证与本机应用

- 定向 212 项通过；完整 Python 1450 项、101 个子测试通过，1 项跳过，全量 Ruff 及 diff 检查通过。Windows 的强制结束进程分支与 POSIX 信号升级分开测试；公开 CI 仍需在对应提交上核验 Linux 全量运行。
- PowerShell 7 和 Windows PowerShell 5.1 的启动包装器分别通过 12 组有效参数和 24 组无效参数检查，覆盖默认值、有限范围、非数、文化格式及一次性模式；使用隔离 mock uv，不读取真实模型配置或启动付费任务。
- 独立真实回环 HTTP 9 项验证 ready/heartbeat 的静默响应、缓慢响应、取消及连接池占满；连接池等待同样受累计截止限制。3 项恢复桥接测试使用实际 BudgetTransport 与合成持久账本，证明 UNKNOWN/DISPATCHING 不再次提交，SUBMITTED 沿用原任务身份查询；它们不是对真实供应商计费系统的故障实验。
- 最终冻结源在真实 Java 协议下经过 37.02 秒代理断连，超过本机 35 秒会话 TTL。同一 QA 进程持续存活，登记确实变为离线；恢复后由它自己产生第二次 registered 和 recovered，内部核对新会话身份，公共心跳继续前进。随后手动停止时，子进程自己的注销请求增加，且在父进程兜底清理前、5 秒内已变为 OFFLINE。
- 独立故障 case 将窗口设为 0.6 秒，观察到 0.703 秒内以 WORKER_RECONNECT_EXHAUSTED 有限退出；另一个 case 在故障等待中停止，0.141 秒正常退出。以上是本机受控故障观测，不是生产延迟或可用性承诺。
- QA 代理只放行本轮 Worker 注册/心跳/注销，以及已完成目标的 TIMELINE 查询；claim、业务回执和其他写入均禁止。最终真实验收中 claim 0、执行器调用 0、范围外请求 0，所有 QA 子进程正常清理；前后核心源摘要一致。
- 本机确认通用 Worker 空闲、无 READY 阶段和 pending journal 后，应用了最终源；仅替换该计算进程，Java 服务保持运行。新进程等待旧会话释放后产生自己的 registered 日志，并实测后续心跳推进，当前在线且资源空闲。
- 更新后，原分析、审核、剪辑请求、对话、导出和字幕共 11 个公共资源摘要保持一致，新增模型/ASR 请求 0。运行证据位于忽略目录 data/runs/worker-runtime-reconnect，不提交原业务内容、密钥或运行日志到公开仓库。

验收还覆盖了两个容易被健康路径遗漏的边界：恢复完成时并发清空共享 deadline 不会产生 TypeError；register/ready/claim 的裸 STALE_ATTEMPT（包括错误标成 retryable 的响应和已处于恢复窗口时）会终止，不能借用已归档 callback 的继续语义形成无界循环。只有归档完整成功后的私有标记允许继续处理下一项。
