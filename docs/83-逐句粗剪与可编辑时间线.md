# 从 AI 候选到可交接的粗剪

面对一小时的课程，剪辑者通常已经知道自己想讲什么，但需要找出对应素材、压到指定时长，并能继续微调每个剪点。LiveCut 先把自然语言需求转成带原句依据的候选，再让剪辑者直接在转写上动手。借鉴 OpenFilm 保留原片、允许在 AI 生成结果上直接编辑和交接的思路，交付格式选用 OpenTimelineIO。[OpenFilm v0.3.1](https://github.com/openfilm/openfilm/releases/tag/v0.3.1) · [OTIO 的时间线、轨道和源区间](https://opentimelineio.readthedocs.io/en/latest/tutorials/otio-timeline-structure.html)

## 剪掉一句，音画如何变化

每条 ASR 原句带原片的起止毫秒与稳定 ID。编辑器读取一个已找到目标的保留区间，将每个区间展开为按原片排序的句子。删掉中间一句时，编译器结束左侧保留区间，从下一条保留句重新起段。前后两句都保留且原本同段时，保留它们之间的停顿。不同来源区间维持各自的入点和出点。成片长度等于各段长度之和。

选自问答的锚句必须保留。人工剪掉普通依据句时，相应证据从新草稿中移除，至少仍须保留一条原有依据。恢复、撤销和重做作用于弹窗内的草稿。点击应用时重新核对请求、视频、转写、版本及当前目标，再走已有的保存、确认流程。源码见 [paperCut.ts](../frontend/src/paperCut.ts) 和 [IntentClipPanel.vue](../frontend/src/IntentClipPanel.vue)。

## 用户要求“60 秒以内”

系统在浏览器 Web Worker 中计算一版建议，可先展开拟剪掉的原句，采用后再试听和撤销。输入沿用当前草稿，手动剪掉的内容继续排除。对于给定的句级边界，必须同时满足时长上限、回答锚点、至少一条依据和最多 12 个区间。

算法按顺序处理每一句的保留或舍弃。状态记录目前已形成几段、上一句是否保留，以及是否已有依据。保留相邻同段句时，将中间的静默时间计入时长。评分考虑候选已有的依据、与目标词的匹配和相邻保留句的连贯性。目标词在该候选中出现越普遍，区分度越低。

每个状态分组保留最短可行路径，再对时长与得分作剪枝。超过每组 32 条路径时抽样，限制偏好排序的计算量，同时保留组内最短路径。因为同组路径之后可以做的编辑及其新增时长相同，最短路径可用于给出不可满足时的最低时长。单次建议处理最多 256 句，超限会提示缩小候选。输出需再通过实际粗剪编译器核对精确时长。语义连贯性由剪辑者试听判断。[时长规划](../frontend/src/paperCutBudget.ts) · [穷举对照和边界测试](../frontend/src/__tests__/paperCutBudget.test.ts)

## 从原片时间到成片时间

| 操作 | 原片区间 | 对应成片区间 |
| --- | --- | --- |
| 保留第一段 | 08:52.763 ～ 09:49.180 | 00:00.000 ～ 00:56.417 |
| 跳过两句补充说明 | 09:49.180 ～ 10:06.007 | 在 00:56.417 接下一段 |
| 保留第二段及回答锚句 | 10:06.007 ～ 10:26.863 | 00:56.417 ～ 01:17.273 |

点击这个剪点，浏览器从 09:47.680 播至 09:49.180，跳到 10:06.007，再播到 10:07.507 停止。导出视频时，FFmpeg 分别裁音轨和画面、重置各段时间戳、按顺序拼接并编码。时长上限作用于整数毫秒的剪辑方案。实际 MP4 的容器时长还受帧和音频包边界影响，交付时以实际文件为准。[剪点试听](../frontend/src/editTimeline.ts) · [媒体导出](../worker-python/src/livecut/media.py)

## 两种交付

- **要发成片**。确认后创建异步导出。Java 冻结所选修订，Worker 读取原片生成 MP4 并解码检查。
- **要继续精剪**。直接下载已确认目标的 .otio 文件，无需创建渲染任务。Java 校验修订号、方案哈希、目标选用情况及适用的人工核对记录，然后将同一组入点、出点写入 V1 画面轨与 A1 音轨。画面轨的证据标记包含保留原句的文字和 ID。源媒体按相对文件名引用，元数据保留原片 SHA-256。将原片放到同一目录，必要时在目标剪辑器中重新链接。毫秒用 OTIO 的有理时间表达，每秒 1000 个时间单位。目标软件可能按自己的工程帧率吸附剪点。[Java 时间线编译器](../backend-java/src/main/java/io/livecut/exports/EditTimeline.java)

按需剪辑的两个只读下载入口如下。

```http
GET /api/clip-requests/{id}/revisions/{revision}/outputs/{outputId}/timeline.otio?plan_hash={hash}
GET /api/exports/{exportId}/clips/{clipId}/timeline.otio
```

带人工选用记录的修订还须提供该版本的 `manual_review_hash`。已有批次按当时确认的版本生成项目文件。直接下载和批次下载均复用原片和既有转写。

## 可以复核的开发样例

- **人工删句**。一段 59:13.137 的真实课程中，已有候选长 94.100 秒，共 7 句。人工删去两句后保留上表的两个区间及 5 条依据。导出的 H.264/AAC MP4 为 77.281337 秒，通过完整解码。对照 6 处原片音频窗口，匹配位置偏差在 7 毫秒以内。
- **时长建议**。同一份初始候选设为 60 秒上限，建议保留 4 句、组成 3 段，计划时长 52.111 秒。实际导出 52.144847 秒，成片在 5.998 秒和 23.138 秒换段，整片通过音视频解码。改为 1 秒时，必留句本身就有 20.856 秒，界面显示最低可行时长。两项均复用了已有候选。
- **浏览器与接口**。桌面和手机宽度下用真实组件、媒体与受控接口回执验证编辑、试听、撤销和确认。独立 Java 集成测试在 MySQL 上实际执行保存、确认和两种 HTTP 下载。CI 使用官方 OTIO SDK 读取并重新序列化响应，核对两轨源区间、成片位置和标记时间。[互操作验证](../scripts/tests/verify-otio-handoff.py)

这些数字描述同一个开发样例。它覆盖媒体生成、编辑约束和交接格式，项目当前没有独立标注集测出的剪辑质量提升数据。
