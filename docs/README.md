## 对原方案的关键调整

| 原方案 | 本方案 | 原因 |
|---|---|---|
| 首轮支持两三小时、多种直播 | 先验证 15～30 分钟、中文单主播、有商品清单 | 先消除最不确定的识别风险 |
| 无商品清单也自动完成实体消歧 | 首版提供 SKU、别名、规格；模糊结果待审核 | 品类相似不能证明同一个 SKU |
| 画面切换用于修正讲解边界 | 语音语义决定讲解，视觉提供支持或冲突证据 | 展示商品与讲解商品可能不一致 |
| 遇到音画冲突再调用视觉 | 先做首中尾少量视觉观察，再对高风险区间加密 | 未观察画面前无法知道是否冲突 |
| Java、MQ、Redis、MinIO 一起上 | 先 Java + Python + MySQL + 本地卷；随后补 MQ/Outbox | 减少初期集成量，保留可靠性主线 |
| 自由 Agent 管整个视频处理 | 固定阶段工作流，LLM/VLM 只做语义判断 | 容易校验、恢复和计费 |
| 先开发，最后准备实验 | 第一天准备小标注集，始终保留原始模型结果 | 避免最终只能演示人工修改后的效果 |

## 时间怎么安排

这是工时估计，不是自然日保证。首次部署、素材获取、API 权限、模型质量可能造成延期。

| 阶段 | 累计投入估计 | 交付物 |
|---|---:|---|
| 技术验证 | 8～12 小时 | 真实视频 → 证据化时间轴 JSON → 3 个可播放切片 |
| 可演示 MVP | 26～40 小时 | 上传、任务、商品时间轴、审核、导出闭环 |
| 秋招展示版 | 约 60～90 小时 | MQ/Outbox、租约恢复、对照评测、120 分钟压力样例、README/演示 |

若每天投入 4～6 小时，MVP 可按约一周安排；完整展示版再按实际工时推进。每天只有 2～3 小时时应相应延长，不能用取消验证来换“完成”。

最快的第一步是技术验证，暂不开发账号、复杂前端或通用调度框架。若 SKU 自动识别不稳，保留“候选讲解定位 + 人工确认商品”的闭环；若视觉没有收益，不把它写成已实现的优化成果。

## 秋招怎么讲

AI 主线：ASR 时间锚点 → 按需求检索与视频问答 → Agent 按需检索原句、观察画面 → 带时间与来源的回答 → 人工确认后剪辑。视觉工具已有实现和受限真实样例；样例成功不等于整体准确率提升，下一步应通过文本与视觉方案的对照评测验证收益。

Java 主线：持久化阶段任务 → 执行器能力与资源准入 → 原子领取、租约和 attempt/token 隔离 → 有限请求预算与恢复 → 不可变提交回执、确认版本和导出快照。MQ/Outbox 仍属于旧规划，不能当作已实现亮点。

优先把两条难点做扎实：**Agent 补充证据与有依据的回答、长任务恢复与版本隔离**。人工剪辑、字幕和素材包用于展示完整交付与人工兜底，不作为模型创新。此前实习中的平台背景与个人贡献应分别陈述；本项目只记录本次真正实现和测试的工作，不提前填写效果提升。
