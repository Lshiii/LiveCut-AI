# LiveCut AI 评测、标注与验收规范

v1.0｜2026-10-23｜所有阈值为建议目标，当前没有实测成绩。

## 1. 为什么先定评测

需要分别证明：能找到商品讲解、能识别正确 SKU、视觉策略值得其成本、任务故障后能恢复。一个演示视频不能同时证明四件事。

保留三类文件：原始模型响应、程序校验后的自动预测、人工审核结果。算法指标只从未经人工修改的预测计算；审核后的可用性另算。合成 Fixture 不进入真实质量报告。

## 2. 最小数据集与划分

### 技术验证集

先取 1 段 10～15 分钟开发样本和至少 1 段独立样本，手工标出全部商品讲解。用于判断链路能否走通和主要错误是什么；样本少时不用于声称泛化性能。

### 秋招展示集

建议 6 段来自独立原始场次的 20～30 分钟录像，共约 2～3 小时：2 段开发，4 段封存测试。争取至少 30 个讲解事件，并实际包含返场、同类不同规格、清单外商品、身份模糊、闲聊、音画错位。

同一原始直播的片段不能跨开发/测试。若来自同一主播、同一商品重复素材，应披露来源并尽量按场次隔离；不要把相邻窗口当独立测试样本。目录和参考图是合法业务输入，商品出现时间标注不能进入模型输入。

先完成完整标注再评测。未标注的剩余时段不能直接当背景；若只标局部，需要声明评测覆盖区间，并裁去未标注部分。

素材不足时，可以自录脚本验证时间映射和恢复协议；必须标注合成/自录来源，其结论不替代真实直播质量。数据规模是建议起点，不具备统计代表性，报告绝对计数。

## 3. 标注规范

目标是商品讲解，不是视觉停留。每个区间包含：

```json
{
  "video_id": "sample_01",
  "annotation_status": "fully_annotated",
  "segments": [{
    "gt_segment_id": "g_001",
    "start_ms": 30000,
    "end_ms": 90000,
    "content_kind": "product_talk",
    "sku_id": "bag_001",
    "identity_status": "matched",
    "audio_visual_conflict": false,
    "boundary_uncertain": false,
    "notes": "合成的标注格式示意，不是真实标签"
  }]
}
```

边界规则：开始针对该商品介绍的第一句为起点，最后相关介绍/演示/报价/答疑句为终点。跨商品切换时分别标注；仅顺带提到旧商品名称不一定是返场讲解，需要有实质内容。暂停、闲聊和纯背景不要强行归属。

SKU 由稳定属性确认，价格不作身份主键；同品牌 50 只装与 100 只装是不同 SKU。语音讲 A、画面展示 B 时分别记录讲解归属与视觉冲突。无法确认规格的样本标 ambiguous，不强行制作精确 SKU 金标准。

建议至少间隔一天复核一次自己的标注，抽查 20% 边界和全部同类不同款案例；有第二位复核者更好。模型输出不能替代人工金标准。对边界本身有歧义的样本单独报告，可记录容忍范围，但主评测口径应在跑测试前固定。

## 4. 对照方案

| 编号 | 方案 | 目的 |
|---|---|---|
| A | 同一 ASR + 商品别名规则 | 最简单、可解释的基线 |
| B | 同一 ASR + 窗口文本模型 | 检查语义判断是否改善定位 |
| C | B + 固定间隔视觉 | 固定视觉预算基线 |
| D | B + 基础观察 + 风险触发局部视觉 | 检查采样策略本身的价值 |

A 的规则在开发集固定，例如句子按别名命中 SKU，只有身份唯一且句间隔不超过设定阈值才合并；阈值、冲突策略必须存配置，不能只运行一个故意很差的关键词示例。

C/D 使用相同目录、相同模型、分辨率与文本提示词。至少做一次相同总图像预算的质量对比，再做一次质量接近时的实际费用对比。D 的首中尾基础采样也计入预算。相同帧数不一定相同 token 成本，所以两者都报告。

不以“每秒抽帧”的极昂贵方案作为唯一对照来证明节省成本。若 D 没有优于 C，应报告并选择更简单的策略。

温度低不保证完全确定；记录模型版本、参数和原始响应。MVP 单次固定运行可先交付，条件允许对开发样本重复运行 3 次观察波动，不能挑最好一次作为主结果。

## 5. 指标定义

### 5.1 商品讲解检测

Temporal IoU：预测区间和金标准交集时长 / 并集时长。使用半开区间，零长度非法。

主指标：类别无关的区间 Precision/Recall/F1@IoU=0.5，补充 0.3 和 0.7。已知 SKU、清单外和身份模糊的商品讲解都进入检测分母；闲聊/背景不算商品讲解。

按同一视频构建满足阈值的预测-金标准候选边，求最大匹配数量、再最大总 IoU 的一对一匹配；相同分数使用稳定 ID 决定顺序。一个金标准不能匹配多个预测，重复候选算额外 FP。评测器要有几组手算可核对样例。

### 5.2 SKU 与归并

端到端 SKU 区间 F1：正确 SKU 且满足 IoU 阈值才算 TP。在完整标注范围内，所有被模型赋予目录 SKU 的预测都进入预测分母；不能与相同 SKU 金标准一对一匹配的算 FP，未匹配的明确 SKU 金标准算 FN。清单外或背景被错误赋予目录 SKU 同样算 FP，已知 SKU 被判未知则产生 FN。

确实无法制作精确 SKU 金标准的 ambiguous 区域单独成表：预先固定忽略规则，例如预测区间有超过一半时长落在该区域时，从主 SKU 评分中排除，但必须另报数量和模型强行赋予 SKU 的过度确认率。忽略规则只能在开发集确定，不能跑完测试后增加忽略区间。

清单外商品另报 unlisted 检出率与“被错误指派给目录 SKU”的比例。对 ambiguous 样本报告转审核是否合理，不把正确请求审核等同于精确 SKU 识别成功。

归并：在已定位并匹配的讲解事件上，比较任意一对片段是否属于同 SKU，计算 pairwise precision/recall。必须同时报告参与的匹配事件数、正例对数和整体检测召回；若没有可评估的正例对，指标记 N/A。错误合并同类不同款计 FP；漏掉返场归并计 FN。

### 5.3 边界

对成功匹配的区间，分别统计起点/终点绝对误差的中位数、MAE、P90；同时列出匹配数与检测召回。只报成功片段的低误差会掩盖漏检。

### 5.4 审核与使用

- 未经人工修改的低风险 SKU 指派精确率与覆盖率同时报告。精确率的预测分母包含全部低风险 SKU 预测；覆盖率 = 低风险且正确匹配的明确 SKU 事件数 / 全部明确 SKU 金标准事件数。
- 人工候选修正率 = 被修改或删除的原始候选 ID 数 / 原始候选数；同一候选多次修改或拆分只计一次，按身份/起点/终点/拆分/误检删除分类。
- 人工新增漏检片段另报数量，有完整金标准时再报告补充了多少漏检事件，不混入候选修正率分子。
- 实际审核时间、有效导出数及失败数。选取同等难度的不同素材做“人工从头检索”和“先看系统结果”的对照，并平衡顺序，避免重复观看记忆效应。
- 个人自测必须注明人数为 1，不能写成普遍用户生产率提升。

### 5.5 工程与费用

- 每小时源视频端到端处理时间、各阶段时间、峰值内存/磁盘、并发配置。
- 每小时源视频总费用与费用分项，实际或估算分开；失败/重试也计入。
- 图像数、图像 token、文本 token、模型请求数、重复请求数、UNKNOWN_OUTCOME 数。
- 故障恢复成功数 / 注入故障数；重试后的阶段复用和额外模型费用。
- 导出成功数 / 实际导出请求数；不把未执行请求算成功。

本地 ASR 不计 API 费，但其硬件与耗时必须披露；云 API 不等于免费计算。没有长时间压测时，不报告 P95 高并发吞吐量。

## 6. 立项与展示门槛

这些是帮助取舍的建议阈值，不代表已达到，也不是保证。

| 关口 | 建议条件 | 未通过时 |
|---|---|---|
| POC 链路 | 真实样本完整处理，时间/引用校验全通过，至少 3 个可播放切片 | 先修链路，不做复杂 UI/MQ |
| POC 语义 | 讲解 F1@0.5 约 0.75、召回约 0.85；标明事件数 | 限定清晰单主播，修分段/ASR |
| 自动归属 | 未经人工修改的低风险 SKU 指派精确率约 0.95，明确报告覆盖率、审核比例和事件数 | 降级为人工确认 SKU，不影响时间轴工具成立 |
| 返场归并 | 自动结果 pairwise precision 约 0.95，同时报告 recall、正例对数与检测召回；样本对不足记 N/A | 保留人工归并，不以少量结果宣称自动归并可靠 |
| 边界可用 | 匹配区间边界中位误差约 5 秒内、P90 约 15 秒内 | 保留建议边界与编辑，降低自动剪辑承诺 |
| 视觉价值 | 同预算质量更好，或相近质量成本更低 | 使用 B 或 C，不包装 D 的优化成果 |
| 工程展示 | 关键故障案例通过；120 分钟样例有完整运行报告 | README 明确支持范围，不声称长视频稳定 |

工程正确性与模型质量分别验收，不能以“模型有误差”为理由跳过旧结果隔离，也不能以状态机测试通过证明 SKU 识别准确。

## 7. 故障注入清单

| 场景 | 必须看到的结果 |
|---|---|
| 两个 Worker 同时领取同一阶段 | 仅一个领取有效，另一个不发起模型调用 |
| MQ 重复通知 | 不造成同阶段同轮重复有效执行 |
| ACK 后 Worker 被杀 | 租约回收，另一个 attempt 执行，之前成功阶段复用 |
| 旧 Worker 晚提交 | STALE_ATTEMPT，不覆盖新结果或导出文件 |
| 完成事务成功但 HTTP 响应丢失 | 重复相同回调返回 ALREADY_APPLIED，不再推理 |
| 最后两个子任务同时完成 | 下一阶段最终激活且只创建一次 |
| 发布前/confirm 后发布器崩溃 | Outbox 可再次发送，任务不丢，重复可处理 |
| 心跳线程仍在但模型卡住 | hard_deadline 生效，任务不会无限 RUNNING |
| 连续 429/网络超时 | 有限重试、退避与预算上限生效 |
| 用户取消分析 | 不创建新工作，旧 token 撤销，尽力停止计算 |
| 导出时继续编辑时间轴 | 旧导出按固定 revision，未偷读最新边界 |
| 浏览器刷新/SSE 断开 | 恢复 DB 最新状态与终态，不要求历史逐条重播 |

多数故障可用可控 FakeProvider 注入；报告应标注模拟供应商。至少再做一次真实 Worker 被杀恢复，核实文件与外部 task_id 的处理。

## 8. 建议报告格式

```text
run_id / 日期 / Git提交 / 数据集manifest哈希
视频来源与授权说明、场次数、分钟数、事件数、目录版本
模型准确ID、Prompt版本、依赖版本、硬件、并发、预算
A/B/C/D：TP、FP、FN、F1、SKU F1、归并指标、边界误差
审核比例、修正类型、人工自测时间
总耗时与阶段耗时、实际/估算费用、token/图像与重试
故障注入通过项、失败项、未执行项
代表性错误与改进计划
原始响应、预测、人工标签与产物路径
```

README 的效果表先填“待测”。没有实测不填“降低 60% 成本”“提升 30% 召回”“百万级并发”或“商业高转化”。展示失败案例和边界，通常比不可复现的漂亮数字更能支撑面试追问。
