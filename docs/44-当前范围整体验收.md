## 本次修复：普通修订不能改写自动分类

原界面会禁用 NEEDS_REVIEW/NOT_FOUND，但 API 原先只验证提交后的状态。调用方保留原区间和证据、仅把状态改成 FOUND 并启用，即可绕过分类限制。该缺口使用合成请求复现，没有修改真实用户方案。

Java 现在读取执行成功时发布的 r0，验证其 canonical SHA256 和初始契约；普通 PUT 必须保留每个 output_id、goal_id 对应关系及 status。确认和新建导出再次对照 r0，不能把上一修订当作新的自动依据。状态或身份篡改返回 `400 INVALID_CLIP_PLAN`；r0 缺失、损坏或摘要不匹配返回 `409 CLIP_PLAN_SOURCE_INVALID`。前端增加相应提示。

合法 FOUND 仍可修改标题、保留区间、排除项、证据和选择状态。历史修订、确认及已创建导出保持可读，未重写数据库历史。独立回归覆盖状态/身份变更、目标互换、合法编辑、旧错误修订、已有导出和 r0 损坏。本次还只读验证了真实请求 `0c7a516a-9050-49a9-a2f9-d7ce99e82064` 的 r0/r1：两个 canonical hash 均匹配，初始校验及新修订校验均通过，仍为 FOUND 1、NEEDS_REVIEW 1、选中 1。
