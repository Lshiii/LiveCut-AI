# 文本请求的有限自动恢复

2026-11-05：针对“前面准备数分钟，文本请求一次失败就结束”的使用问题，为话题解析与按需求剪辑增加同一套恢复策略。语音识别仍复用原有任务与产物，不把文本失败变成重新提交整段视频。

## 执行策略

默认每个逻辑文本请求最多 3 次实际尝试，单次最多 90 秒，从该逻辑请求开始至结束最多 240 秒。Socket 连接、TLS、发送、响应读取共同受单次实际时间限制；持续收到空白保活也不能无限延长。DNS 解析仍依赖系统解析器，不承诺强制中断系统 DNS 等待。使用同步受限网络流，超时关闭本次流后才进入下一次，不通过遗留后台线程并发发送付费请求。

连接异常、读取超时、HTTP 408/429/5xx进入有限恢复。普通参数错误不盲目重试；认证失败优先切换已配置且允许的备用服务，没有备用时直接给出配置原因。指数退避从 1 秒开始，等待受总时间与任务租约约束。没有剩余预算、租约失效、取消、响应落盘失败或账本不可用时停止新增调用。

主服务通常先尝试两次，再将第三次交给唯一备用服务；存在两个备用时每个服务各占一次。主服务认证失败可提前切换。切换沿用相同需求与候选原句，并按目标服务的 OpenAI compatible / DashScope 原生协议重新编码，不把其他服务的鉴权头带过去。

2026-11-06 增加[同阶段跨窗口熔断](./41-文本服务跨窗口熔断与恢复.md)：上述顺序适用于没有近期故障的默认路线。主服务连续故障后，新逻辑窗口可优先可用备用；已经冻结的请求继续按原路线重放或恢复，次数、时间和预算上限不变。

## 本地配置

密钥只存放在被忽略的本地配置或环境变量中。示例均为占位，不包含实际凭证：

```dotenv
LIVECUT_TEXT_API_STYLE=openai
LIVECUT_TEXT_BASE_URL=https://api.deepseek.com
LIVECUT_TEXT_MODEL=deepseek-flash
LIVECUT_TEXT_API_KEY=REPLACE_WITH_PRIMARY_KEY
LIVECUT_TEXT_MAX_ATTEMPTS=3
LIVECUT_TEXT_ATTEMPT_TIMEOUT_SECONDS=90
LIVECUT_TEXT_TOTAL_TIMEOUT_SECONDS=240
LIVECUT_TEXT_RETRY_BACKOFF_SECONDS=1
LIVECUT_TEXT_FALLBACK_MODELS=qwen-plus
LIVECUT_TEXT_FALLBACK_API_KEY=REPLACE_WITH_BACKUP_TEXT_KEY
LIVECUT_TEXT_FALLBACKS_JSON=[{"name":"bailian","base_url":"https://dashscope.aliyuncs.com","api_style":"dashscope","model":"qwen-plus","key_env":"LIVECUT_TEXT_FALLBACK_API_KEY"}]
```

Java 与 Worker 均读取一致的配置。新分析与新剪辑请求分别冻结允许的备用模型名单；调整部署配置不会改写已有请求的名单。旧请求没有名单时不会擅自改用不同模型。备用配置要求 HTTPS、安全名称、独立文本密钥变量和完整字段；无有效配置不能声称已经切换成功。

## 账本与恢复

每次实际尝试先通过 Java 的领取凭证和原预算检查，再预留独立 model_call。主调用和重试、备用调用共享原 max_text_calls，不会因为“自动恢复”绕过上限。

超时只能说明本地没有拿到完整结果，旧调用可能仍在供应商侧执行或计费。因此旧记录保持 UNKNOWN_OUTCOME，新尝试使用新的有限序号，独立记录实际模型、请求及用量。系统不承诺供应商支持幂等或只计费一次，也不伪造旧调用结果。

尝试序号绑定逻辑输入与阶段，而非进程启动次数。重启后先复用有哈希验证的成功响应，跳过旧的未知调用，再按原剩余次数恢复；不会重发同一旧 dispatch。策略和服务顺序固化在受限的恢复文件中，改变配置后不能重置原尝试次数。已完成的前置 MEDIA/ASR 阶段保持完成；已有文本成功窗口通过原始响应重放继续，人工修订独立保留。

`text-execution-trace.json` 保存实际执行的服务、模型、尝试序号和状态，作为来源绑定的产物进入 manifest。原结果中的 `text_model_id` 是该请求配置的主模型；发生备用调用时，以执行 trace 与 Java model_call 记录核对实际使用模型。

## 可见进度与边界

Worker 使用带有效租约的 `/internal/stages/{id}/text-progress` 回调发布安全状态。页面展示正在请求、等待重试、切换备用、成功或耗尽，以及尝试次数、阈值和等待时间；公开数据不包含服务地址、密钥或原始供应商响应。分析与独立剪辑各自更新自身状态，旧话题草稿不被覆盖。

这套机制处理的是文本服务的短暂故障，不能保证无效密钥、余额不足、输入错误或持续性平台故障最终成功。达到次数、时间或预算上限时明确显示原因，并保留已经完成的准备工作。

## 验证记录

本轮 Python 全量 1067 项及 98 项 subtests、Java 全量 209 项、前端 91 项测试通过，类型检查、构建与 Ruff 通过。自动测试覆盖临时故障后成功、切换备用、认证与参数错误、预算耗尽、结果未知、重启后次数不重置、取消和租约隔离，以及安全进度解析。真实本地慢流测试连续发送空白保活，0.15 秒测试阈值触发超时，并验证连接关闭。

真实 KV Cache 请求通过新执行链路完成：2 次 DeepSeek 文本请求均为 SUCCEEDED，0 次新 ASR，多区间成片完整解码通过，原分析与原话题审核不变。这次真实主服务没有发生故障；重试和跨平台切换由合成故障注入验证，不写作真实平台故障恢复或准确率提升。

全量验证还发现领取任务时的一个数据库死锁：带锁阶段查询因 ORDER BY id 选择主键扫描，锁到了另一个任务的阶段，与全局容量锁形成循环。查询强制使用以 job_id 开头的 uk_stage_identity 索引缩窄范围；真实 MySQL 回归验证锁住任务 B 的阶段时，任务 A 仍可领取。
