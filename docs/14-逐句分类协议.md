# 逐句分类与分段输出协议

2026-10-24～25。此文记录逐句协议的演进。v9 位置数组在真实首窗失败；当前 v10 以源语句 ID 为键，尚待真实验收。最终时间轴仍为 schema 2.0，没有识别精度提升结论。

## 为什么调整

此前模型返回讲解段的首尾 ASR ID，由程序展开范围。真实 30 分钟开发片段在三次 SEGMENT 执行中出现重叠和遗漏，最后一次仍有七个 ID 被重复分配，严格校验拒绝继续。失败任务和原响应保留，记录见 [集成验收](./13-MVP集成与验收.md)。

v9 将模型的工作改为按固定顺序逐句分类。每个窗口仍有核心语句与前后上下文，独立商品发现步骤保持原有语义；上下文只辅助理解，不产生额外分类项。

## v9：位置数组（历史协议）

输入提供 `output_protocol=dense-core-assignments-v1`、`assignment_count`、有序 `core_utterance_ids`、原转写和已有证据。下例只有两个核心语句，是合成协议示例：

```json
{
  "products": [
    {"label": "tmp1", "category": "面膜", "variant_description": ""}
  ],
  "assignments": [
    {"content_kind": "product_talk", "identity_status": "identified", "product_labels": ["tmp1"]},
    {"content_kind": "non_product", "identity_status": "not_applicable", "product_labels": []}
  ]
}
```

`assignments` 必须是与核心语句数量严格相等的数组。第 i 项仅对应第 i 个核心 ASR 句；模型不能输出 ID、索引、起止范围或时间。分类响应的顶层、商品与分类项均按严格字段集合校验，重复 JSON 对象键、缺项、多项、旧 `segments` 范围格式、非法标签和身份组合均失败，不截断或补齐。独立商品发现步骤仍使用既有解析规则，没有把新解析器的约束宣称为对所有模型步骤的改动。

程序绑定可信 ASR ID 后沿用原身份与分段校验，再按既有规则合并相邻且类别、身份和内容类型相符的项。unknown、ambiguous、mixed、non_product 均保留原语义；中间出现其他商品或闲聊，返场仍是另一个区间。正式毫秒边界继续来自原 ASR 时间戳，人工审核仍可修改并留下独立修订。

这能从协议上避免生成互相重叠的范围或漏掉某个核心 ID，**不能验证模型是否理解了每句话，也不能发现它用错位置或错误分类**。等长合法输出、通过业务 Schema 和通过代码测试，都不能代替定位质量评测。

## 原始响应与恢复

Provider 原始响应先完整落盘，解析不会重写该文件。格式失败仍最多修复一次；无效输出不转成成功结果。

提示词版本改为 `catalog-free-v9-dense-core-assignments`，输出协议进入运行指纹，最终 pipeline_version 为 `catalog-free-visual-text-v4`。旧输出目录不能按新协议恢复，会明确报 INVALID_CHECKPOINT；旧 schema 2.0 最终结果与审核记录继续可读。新分类请求的 body 与旧范围请求不同，不能把旧范围响应作为新协议缓存命中。输入完全相同的独立发现请求仍按既有请求身份判定缓存，不人为改写旧调用记录。

## 验证与下一关口

离线检查使用合成转写、模拟 Provider 和请求账本回放，覆盖完整分类、缺项/多项、上下文、32 句窗口、未知与混合身份、返场、跨窗口合并、重复 JSON 键、原响应不变，以及旧/新请求缓存隔离。模拟响应只证明协议，不是实际模型效果。

本机 Ruff 通过，完整 Python 复验 **302 项及 98 子测试通过**。首次全量运行曾有一项既有导出测试的 FFmpeg 转码超过 300 秒，其他 301 项通过；进程按超时机制退出后，原失败用例单独复验及随后完整复验均通过，没有修改媒体代码、超时或该测试。首次失败摘要与后续原始复验日志保存在本地忽略目录 data/runs/dense-protocol/，没有将首次失败删去或当作通过。请求沿用 Provider 默认输出容量，尚未用真实模型验证长窗口是否截断，也没有新增 token 上限或宣称费用保证。

原 30 分钟任务保持 FAILED，TEXT 16/24、ASR 1/1、SEGMENT attempt 3，未通过修改数据库或提高预算继续执行。后续以独立的新运行验证真实十个窗口、全局语句覆盖和正式成片；复用 ASR/OCR 必须经过显式输入、版本与哈希校验，不能把其他任务的结果引用直接冒充新任务产物。

## v9 真实运行结果

新建 generation 2 任务 `7e2c6b9a-0885-4fb7-9d06-c0b33c9a0098`，沿用同一份 1800.017 秒开发素材，独立上限 TEXT 24 / ASR 1。正常 Worker 的 MEDIA、ASR 均 attempt 1 成功；ASR 是一次新的真实提交，没有将旧任务产物冒充缓存。

SEGMENT 首窗有 28 条核心 ASR 语句，首次完整响应只返回 27 项，唯一一次格式修复仍返回 27 项，严格校验拒绝。最终该阶段 attempt 1 FAILED、TIMELINE BLOCKED，完整分析、审核与新成片均未产生。立即停止，没有自动再试或提高预算。新任务累计 TEXT 3/24、ASR 1/1；四条 Provider 请求均取得响应，不能把请求成功当作业务分段成功。

本轮文本 usage 合计 11,896 tokens，包含被拒绝的响应；不是人民币账单。Worker 执行 wall time 为 MEDIA 2.000 秒、ASR 41.953 秒、SEGMENT 49.328 秒，包含模型等待，不包括任务排队和运行器准备，且整项业务最终失败。原 generation 1 失败任务的完整公开快照在每阶段执行前后均相同。

这次结果表明固定数组仍依赖模型精确计数。下一次协议调整需要能精确指出缺失的源语句 ID；不截断、补项或默认归类来把 v9 的 27 项拼成 28 项。原响应、账本、诊断和目标任务隔离检查保存在本地忽略目录 data/runs/mvp-30min-v9/。

## v10：以源语句 ID 为键

当前 output_protocol 为 `keyed-core-assignments-v1`，提示词为 `catalog-free-v10-keyed-core-assignments`，pipeline_version 为 `catalog-free-visual-text-v5`。下面是仅有两个核心语句的合成结构示例，实际键必须来自本窗口 core_utterance_ids：

```json
{
  "products": [{"label": "p1", "category": "面膜", "variant_description": ""}],
  "assignments": {
    "u1": {"content_kind": "product_talk", "identity_status": "identified", "product_labels": ["p1"]},
    "u2": {"content_kind": "non_product", "identity_status": "not_applicable", "product_labels": []}
  }
}
```

键集合必须精确等于核心 ASR ID 集合。JSON 重复键、缺失键、未知键、上下文键以及非法分类值均拒绝。缺失反馈最多包含 16 个完整的可信源 ID，单个 ID 的 JSON 长度不超过 96；同时给出总数和省略数。未知模型键只计数，不回显其文本作为修复指令。

对象的键顺序没有语义，程序按可信 ASR 原顺序取出每个 ID 的分类，再执行已有身份与相邻合并校验。没有默认填入、丢弃额外项或把重复项选一个放行。旧 v9 数组和 v8 范围格式明确拒绝；新提示词、协议与状态指纹隔离旧分配响应，旧最终 Schema 2.0 结果继续可读。独立发现、窗口划分、归类粒度与合并规则保持原样。

v10 离线完整检查 **314 项及 98 子测试通过，Ruff 通过**。覆盖缺失 ID 的精确反馈、键乱序、上下文/未知键、恶意文本与超长可信 ID 的有界反馈、重复 JSON 键、旧协议拒绝和请求缓存隔离。原始响应不改写，语义规则 AST 与上一版本相同。私有验证记录位于 data/runs/keyed-protocol/。这些测试仍不证明真实模型会完整分类，更不证明商品归属正确。

后续验证使用原 generation 2 任务的正常重试入口，保留已成功的 MEDIA/ASR。原 TEXT 3/24、ASR 1/1 已用额度继续计入账本；不增加预算、不重置 attempt，不把旧响应改写成新结果。
