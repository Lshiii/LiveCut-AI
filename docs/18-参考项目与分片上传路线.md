## LiveCut 的差异化主线

DOVideo-AI 的公开定位是把长视频组织成可检索、可继续追问的知识，并提供多种分析目标。LiveCut 聚焦电商直播素材整理，最终交付商品片段及其审核、导出记录。

| 维度 | LiveCut 当前基础 | 后续可形成的产品亮点 |
|---|---|---|
| 商品讲解定位 | 无清单类别发现、逐句归属、原 ASR 毫秒锚点；区分讲解、闲聊、混合内容 | 商品切换附近的局部复核与边界精修，质量单独评测 |
| 返场管理 | 多个独立区间关联商品；确认后按商品选择导出 | 审核统一返场归属，再生成同商品的多段合集。合集拼接尚未实现 |
| 可核对依据 | 语音证据、OCR 状态、不确定原因、原始预测独立保留 | 从商品卡片直接定位证据和待处理冲突，辅助审核 |
| 审核到成片 | 不可变修订、精确确认版本、冻结导出、MP4 与文件清单校验 | 批量整理一场直播的商品素材，并保持每段与原视频位置的对应 |
| 可恢复与成本 | Java 独占业务状态，阶段租约、过期结果隔离、调用账本、次数预算、显式 ASR 复用 | 上传到导出的统一恢复入口，区分上传失败、模型失败和导出失败 |

这些基础上传能力本身不作为独创算法。项目差异化体现在商品讲解语义、返场审核和可交付成片的完整业务流程。已有 30 分钟分析及三段开发审核成片的事实见 [完整验收](./17-30分钟完整验收.md)，未测的质量和效率收益不提前写成成果。

## 分片上传的适配边界

沿用现有 Java / MySQL / 共享文件存储，先完成单人本机版本。当前 MP4、1 GiB 上限、服务端 SHA256、HEADER_CHECKED 与后续 MEDIA 完整探测继续有效。上传完成只注册视频来源，用户创建分析任务时才使用模型预算。

参考上传服务以 Redis 保存会话和完成回执，MinIO 保存分片，合并时计算 MD5。LiveCut 需要把上传结果纳入已有不可变来源协议，因此独立实现以下保证：

1. **明确文件身份**：初始化绑定文件名、总字节数、整文件 SHA256、服务端决定的片规格。浏览器以内容摘要识别续传，文件名、大小和 lastModified 只用于显示与快速提示，不能单独证明是同一内容。前端摘要计算应分块进行，避免一次读取整个大文件。
2. **分片幂等**：每片验证索引、精确长度和 SHA256。同一索引、相同内容的重传返回原接收结果；不同内容返回冲突，不能覆盖已确认分片。确认字节数不因重试重复累加。
3. **服务端进度真源**：MySQL 保存上传会话和分片回执，status 返回会话状态、已接收片、确认字节数、过期时间，完成后返回最终 video_id。浏览器刷新后需重新选择原文件，再查询服务端进度；网络错误不能被当成会话失效而自动从零开始。
4. **合并与上传隔离**：开始合并前冻结可写状态。合并检查完整分片序列、总长度和最终 SHA256，文件发布前继续原 MP4 头校验。合并期间不允许迟到分片改变输入。
5. **完成回执持久化**：固定目标 video_id；视频注册与上传完成状态在同一数据库事务提交。响应丢失、Java 重启、重复 complete 都要查回同一结果；数据库提交结果不明时保留来源，按现有规则核对，不能直接删除或再次注册。
6. **故障和资源边界**：合并占用有界，长文件合并不在请求主链路长期持有数据库锁。合并领取需有租约/令牌和失效恢复；临时文件有过期清理与空间限额，清理范围仅限该会话自己的上传目录，不能删除已发布视频。

参考代码的初始化没有绑定期望字节数或摘要，分片路径也未见逐片摘要校验；complete 的数据库注册与 Redis 完成回执是先后两步。上述收口是针对 LiveCut 的实现要求，不代表已运行并复现参考项目的故障，也不推断其外部部署配置。参考测试使用模拟 Redis、MinIO 和网络响应，不能代替我们自己的真实大文件验收。

## 拟定接口与交付顺序

| 接口 | 职责 |
|---|---|
| `POST /api/uploads` + Idempotency-Key | 创建或找回同一初始化请求；返回上传 ID、固定片规格、过期时间 |
| `GET /api/uploads/{id}` | 查询持久进度、缺片、合并状态与最终 video_id |
| `PUT /api/uploads/{id}/parts/{index}` | 发送一个二进制片，携带片 SHA256，返回幂等回执 |
| `POST /api/uploads/{id}/complete` | 校验并进入合并；可重复查询或重放，最终关联同一来源 |

页面将区分“校验文件、上传、暂停、合并、完成”，展示已确认字节、续传数量和有限重试。暂停停止客户端发送并保留服务端进度；刷新后重选文件可续传。合并进度不伪装成上传字节进度。每个功能完成后按现有规则验证、提交并推送。

先定下以上契约，再分别实现后端持久会话与文件接收、前端续传交互，最后一起进行真实验收；接口细节和默认片大小以实现时文档为准。跨会话的全局内容去重/秒传单独设计，不能把同一会话的幂等完成说成全局秒传。

## 本功能必须通过的验收

- 使用现有约 160 MB 真实 MP4，中途暂停、刷新后重选同文件，只补缺片；Java 重启后已确认进度保留。
- 三个并发片、乱序、同片重复、请求响应丢失均不重复计数；同一索引的不同内容明确冲突。
- 同名、同大小、同 lastModified 但内容不同的文件不能错误续接；错误片 SHA、长度、片号均拒绝。
- 缺片不能完成；并发 complete、完成响应丢失与完成后迟到上传，最终只关联一个视频来源。
- 合并前后注入进程中断，按原会话恢复；过期清理与合并并发时，已发布来源保持可读。
- 合并后视频 SHA 与原文件一致，Range 播放及现有 MEDIA 探测保持兼容；验收不发起新模型请求。
- 上传过程、暂停、恢复、异常提示和浏览器真实大文件行为都要核对，不能只凭 mock 测试宣布完成。

后续优先级为 **分片上传 → SSE 快照与断线恢复 → OCR 证据复用/失败诊断 → 持久 ASR 分块及 MQ/Outbox → 质量评测与作品整理**。识别精度和视觉计费方案保持此前约定，质量优化后置。
