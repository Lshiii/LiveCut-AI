# 阶段失败诊断与恢复建议

2026-10-26，已完成全量回归、MySQL 事务与重启、真实 Worker 和浏览器联合验收。

## 要解决的问题

原有阶段和导出条目只公开 `error_code`。长录像分类在某个窗口失败时，页面无法区分缺少核心语句、多返回上下文、分类值错误或修复请求中断；预算耗尽、调用结果未知、缓存损坏也需要不同的处理方式。

本轮增加可持久化的结构化摘要。诊断用于说明原因，不授予重试权限，也不改变调用预算、有限执行次数或旧结果隔离规则。Java 继续唯一推进业务状态。

## 写入协议

Worker 原有 fail 回调的四个字段保持兼容，可新增可选 `diagnostic`：

```json
{
  "attempt": 2,
  "run_token": "synthetic-example-only",
  "error_code": "INVALID_MODEL_OUTPUT",
  "retryable": false,
  "diagnostic": {
    "reason_code": "ASSIGNMENT_KEYS_MISMATCH",
    "window_index": 8,
    "window_count": 10,
    "missing_core_id_count": 0,
    "extra_context_id_count": 3,
    "unknown_key_count": 0,
    "non_core_key_count": 3,
    "value_error_count": 0,
    "format_repair": "FAILED_VALIDATION"
  }
}
```

以上是合成协议示例，不是一次真实模型调用。公开快照完全不包含 `run_token`。

Worker 只能提交以下上下文，Java 拒绝其他字段：

| 字段 | 约束 |
|---|---|
| reason_code | 与实际错误码匹配的受控枚举，可省略 |
| window_index / window_count | 必须成对，0-based，`0 <= index < count <= 10000` |
| missing_core_id_count | 缺少的核心语句数量 |
| extra_context_id_count | 多返回的已知上下文数量 |
| unknown_key_count | 不属于本窗可见输入的键数量 |
| non_core_key_count | 全部非核心键数量；三项都存在时必须等于上下文数加未知数 |
| value_error_count | 已返回核心项中分类值错误的数量 |
| format_repair | NOT_ATTEMPTED / FAILED_VALIDATION / INTERRUPTED |

五项计数均为 0～1,000,000 的严格整数，不接受 bool、小数或数值字符串；对象最多 4 KiB。`FAILED_VALIDATION` 仅用于 `INVALID_MODEL_OUTPUT`。不得提交模型原文、异常消息、提示词、语句 ID 列表、URL、路径、Token 或堆栈。

Java 在 fail 的同一事务中先检查当前 attempt、token、父任务和租约，再校验诊断。随后绑定实际 `error_code`、数据库 attempt 和 `schema_version=1`，派生 category / suggestion_code，写入 V7 新增的 nullable `job_stage.diagnostic_json`。无诊断的旧 Worker 回调仍会在新失败时生成安全的基础摘要；非法诊断不会只写入一半状态。

## 读取与生命周期

分析阶段 `stages[].diagnostic` 与导出条目 `clips[].diagnostic` 使用同一结构。SSE 沿用完整快照，不建立另一份诊断状态或历史事件日志。

- FAILED / RETRY_WAIT 保留当前执行的诊断。
- 手动重试、领取新执行和成功完成时，与 `error_code` 一起清除。
- 超时和父阶段失败由 Java 生成自身原因，不沿用旧执行的窗口细节。
- 旧 token 的回调不能覆盖新执行的诊断。
- 历史 NULL 记录读取时不补写、不临时派生，新增字段完全省略；不改已冻结审核或导出快照。
- 无效、损坏或绑定不匹配的存量诊断安全省略，不回显任意数据库文本。

Python 的 `SegmentationError.diagnostic` 从实际校验分支生成枚举和计数，Worker 再做白名单过滤。初次和格式修复后的校验错误都写入私有本地调用记录，最后一次校验的计数不会被前一次覆盖。fail 的精确 payload 随 journal 持久化，丢失回调响应只重放该 payload，不重新计算或提交模型。

`max_calls=0` 现在与 Java 的零预算配置一致：非空分析在请求前以 `BUDGET_EXHAUSTED` 失败；负数、bool 和其他非法类型仍为配置错误。超过窗口数量上限与请求预算不足使用不同 reason_code。

## 页面行为

页面展示固定中文文案、1-based 窗口位置、数量和修复状态；不显示语句列表或模型原文。可选诊断须匹配当前 attempt / error_code，无效或未来不支持的诊断只被省略，任务主状态和操作权限仍正常更新。旧错误记录保留错误码和无详细诊断提示。

| 原因 | 建议 |
|---|---|
| 输出格式或分类结构错误 | 检查格式和规则，再依据服务端操作权限处理 |
| 原任务预算不足 | 新建足够预算的任务；重试不增加原预算 |
| 供应商调用结果未知 | 先恢复或核对既有调用，避免重复提交 |
| OCR 缓存争用 | 等待拥有者，有限次数内退避 |
| 缓存容量、完整性或路径异常 | 先排查对应问题，再恢复任务 |
| 前序失败或执行超时 | 分别检查前序原因或 Worker 状态 |

### 真实 Worker 与重启

在已有 30 分钟原视频上创建独立验收任务 `419c4a6b-ec14-434e-8fe3-77f2b668744c`。MEDIA 正常抽音频，ASR 严格复用已发布转写，OCR 命中已核验的 16 帧缓存。文本和 ASR 提交预算都设为 0，生产 Worker 在文本请求前返回 `BUDGET_EXHAUSTED`；Java 持久化并公开预算类别及新建足够预算任务的建议。

本轮 Worker 不初始化 OCR、不重新抽帧、不提交外部模型调用。重启 Java 后，该失败任务的公开响应字节完全一致，浏览器展示“重试仍使用本任务原预算，不会增加可调用次数”。这是一条真实的预算保护失败路径，不是一次新的成功商品分析。

### 受控故障注入

页面请求重试后，旧错误和诊断消失；新 claim 为 attempt 2。对该独立任务注入含自由文本的非法诊断，返回 400，状态和版本不变；再用旧 attempt 的凭证提交，即使诊断本身非法也先因执行权失效返回 409，当前状态不变。

随后明确注入格式错误摘要：第 9/10 窗、缺少 2 项、多余上下文 3 项、未知 0 项、分类值错误 1 项、修复后仍未通过校验。页面通过 SSE 展示对应中文说明，没有手动刷新，没有回显模型内容或 ID 列表。这些数字是故障注入数据，仅验证协议和界面，不是本次真实模型输出。验收任务最终取消收尾，模型预留仍为 0。
