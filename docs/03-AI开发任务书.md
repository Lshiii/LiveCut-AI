# LiveCut AI：交给 AI 的分阶段开发任务书

> 当前需求已调整为无商品清单自动识别。本文保留立项参考，涉及SKU目录的前置要求由 [最新执行需求](./05-无清单识别需求变更.md) 替代。

v1.0｜2026-10-23｜执行计划，尚未创建业务实现。

## 1. 最快完成的方法

先用一个真实视频走通算法，再让前后端围绕同一份契约开发。不要一次让 AI“生成整个完整项目”，然后同时处理环境、接口、模型和状态机问题。

推荐先按约 26～40 小时拿到可演示 MVP，再累计投入约 60～90 小时做成可信秋招作品。时间包含人工阅读、调试、素材标注和集成；受每日投入、模型权限和素材质量影响，不保证自然日完成。

最快前两个工作日：

- 第一个工作时段：准备真实视频、SKU 清单、少量金标准，验证 FFmpeg、ASR 时间戳与 API 可用性。
- 第二个工作时段：实现文本分段和 SKU 候选输出，生成可验证的 JSON，实际导出至少 3 个片段。
- 第二天结束前做一次判断：识别是否值得工程化？分段差则缩小场景；SKU 模糊则保留候选确认；视觉尚无收益则不阻塞主闭环。

每天结束留下一个能重跑的入口、当日验收证据和下一任务。AI 辅助省掉的是样板劳动，业务定义、错误分析、标注和关键状态协议仍需要你自己理解。

## 2. 建议目录

未来代码单独放在 `LiveCut-AI/`，本目录作为设计输入；不要改动现有 ai-picture-editor、Easel 和简历。

```text
LiveCut-AI/
  README.md
  AGENTS.md
  docs/                   # 本开发包的设计文档与决策记录
  contracts/              # JSON Schema、接口契约与合成 Fixture
  backend-java/           # API、状态机、领取、审核、导出
  worker-python/          # 媒体、ASR、语义分段、视觉适配器
  frontend/               # Vue 工作台
  eval/                   # 标注规范、评测器、基线与报告
  infra/                  # Compose、环境变量模板
  data/                   # gitignore，本地视频、目录、原始运行结果
  scripts/                # 一键小样运行、结果核验、报告命令
```

POC 尽量使用后续 Worker 的同一套 Python pipeline 函数，CLI 只是入口，避免先写一次 Demo 后来全部重做。

## 3. 每个任务都给 AI 的工作约束

```text
你正在实现 LiveCut AI 个人秋招项目，同时面向 AI 应用和 Java 后端。
先读取 docs/01-PRD.md、docs/02-技术路线.md、当前任务，以及已有 AGENTS.md。
遵守现有工程状态，只实现本任务和必要的最小依赖。

约束：
1. 时间全部为原视频全局毫秒；LLM 引用 ASR ID，程序生成正式时间。
2. Java 是业务状态唯一写入方；Worker 不直接更新 MySQL 业务表。
3. Java/MySQL 持久调度先跑通，MQ 之后加入；不引入 Redis、通用 DAG、Agent 框架。
4. 模型结果、合成 Fixture、录制回放和人工审核结果必须区分。
5. 只在明确配置 mock 时使用 Fixture；真实 provider 失败不能悄悄返回假结果。
6. 不编造模型字段、SDK 签名、费用和测试结果。查对应版本官方文档并做小样验证。
7. 对状态并发、时间映射、导出版本做有意义的测试；不为简单样板代码堆测试。
8. 不提交密钥、大视频、临时签名URL；不修改已有简历或其他项目。

完成后报告：改了什么；如何运行；实际通过的验证与关键输出；未验证部分；下一任务。
如果验收不通过，先修复或给出明确阻塞证据，不得把下一阶段当作本阶段完成。
```

可以将这些约束放入新仓库 AGENTS.md，但当前文件本身只是提示词模板。

## 4. 有依赖顺序的任务

### T0：素材与契约，约 2～3 小时

交付：一段 10～15 分钟开发视频、一段独立小样、包含 3～8 个 SKU 的清单、手工标注与稳定 Schema。素材优先有返场、同类不同规格和模糊片段。

验收：播放起/中/末确认时间轴；明确哪些视频属于开发、哪些属于测试；合成示例通过 Schema，错误时间/未知引用能被业务校验拒绝。

可复制任务：

```text
执行 T0。建立独立 LiveCut-AI 目录，将设计文档和 contracts 作为输入。
先实现结果契约的加载与校验，提供合成示例，标明 data_kind=synthetic_fixture。
建立 catalog 输入格式、数据集 manifest 和人工标注模板。
不生成伪造的真实视频分析报告；真实视频路径由本地配置提供。
提供一个命令验证 Schema 和跨字段约束，并输出通过/失败摘要。
```

若拿不到真实素材，合成视频只能证明流水线行为。不得因此宣称真实直播识别有效；应尽早解决素材来源，而不是继续做空界面。

### T1：媒体与真实 ASR，约 3～4 小时

交付：ffprobe、音频提取、ASR Provider 适配器、原始转写、统一 utterance JSON、模型调用记录。先选择一种真实 ASR，不同时实现所有备选。

验收：至少 1～3 分钟音频真实调用成功，句子时间合法；再跑完整开发样本，手工检查 3 个时间锚点。保存外部 task_id 后优先继续查询；无 task_id 且提交结果不明时记录 UNKNOWN_OUTCOME，按供应商幂等能力、重试策略和剩余预算决定是否重新提交，不能盲目重复计费。

```text
执行 T1，复用 T0 的数据契约。
实现 MediaProbe、AudioExtractor 和 AsrProvider 接口，默认使用已确认可用的托管文件 ASR REST 路线。
根据官方接口处理本地音频上传、临时资源或 HTTPS 文件地址，不能把本机路径当远程URL。
异步提交后保存 provider_task_id；原始响应和统一 utterance JSON 都落盘。
时间戳缺失应明确报错，不让语言模型补时间。提供 CLI 和真实运行核验步骤。
没有可用凭证时完成适配器与显式阻塞说明，不能把 mock 测试写成真实调用成功。
```

### T2：语义分段与初次导出，约 3～5 小时

交付：带上下文的文本窗口、结构化模型输出、目录匹配、时间映射、候选 JSON、最小 FFmpeg 导出入口。

验收：真实样本输出可播放片段；每段有有效证据 ID；返场保持独立；同类不明确不强行归并；未手改预测先跑评测。

```text
执行 T2，仅实现 ASR+LLM 基线，不先接视觉或数据库。
以180秒核心窗口和前后各30秒上下文为初值，使用句子中点确定唯一窗口归属。
模型只能返回输入中出现的句子ID、SKU候选和原因码，程序负责正式毫秒时间。
保留原始响应；校验失败最多进行一次受控格式修复，仍失败显式记录。
输出完整 analysis-result 和3个按预测区间裁出的MP4，检查ffprobe时长。
用开发样本算初步检测指标，输出至少5个错误/未决案例；没有5例则列出全部。
```

**M0 关口：**至此累计约 8～12 小时。没有真实 ASR/文本结果或主要区间不可用时，先解决模型和范围，暂不进入 UI/MQ。

### T3：Java 持久任务骨架，约 4～6 小时

交付：Flyway、核心业务表与最小调用账本、创建任务、固定阶段依赖、claim/heartbeat/checkpoint/complete/fail、持久预算预留、租约扫描、文件 StoragePort。导出片段也使用统一 job_stage 执行协议。

验收：用 FakeWorker 重复领取仅一次成功；完成回调重复不重复推进；过期 token 无效；最后两个并行子任务完成能可靠推进。FakeWorker 验证的是协议，不是模型质量。

```text
执行 T3。先用假计算结果验证Java任务协议，不接MQ。
实现MySQL固定阶段任务、原子claim、attempt+run_token fencing、租约和hard_deadline。
心跳不废掉本次领取凭证；任务超时回收与完成回调按数据库条件更新竞争。
Java单独负责重试；下一阶段有唯一约束，父任务串行检查依赖。
返回明确的ACCEPTED、ALREADY_APPLIED、STALE_ATTEMPT，支持领取响应丢失后的同请求查询。
验证并发和旧回调场景，提供可运行的集成检查命令和数据库状态证据。
```

### T4：真实 Worker 接入，约 2～4 小时

交付：空闲槽位领取、调用已有 pipeline、独立心跳、检查点、attempt 独立目录、manifest 回调、停止/失败传播。

验收：完成真实视频任务；杀死一次 Worker 后能够恢复；已成功阶段不重新运行；完成回调超时只重试回调。记录外部推理可能重复计费的边界。

```text
执行 T4，复用T1/T2模块，不重写算法。
Worker从Java领取阶段后执行，只通过内部API改变业务状态。
文件写入当前attempt专属目录并生成哈希manifest，旧attempt不能覆盖公共结果。
模型或FFmpeg都设超时；hard_deadline后不继续无限心跳。
模拟一次Worker被杀与一次完成响应丢失，核对恢复位置和调用次数。
```

### T5：审核工作台，约 4～6 小时

交付：上传、目录导入、任务列表/状态、video 播放与时间轴、ASR 证据、商品修正、边界编辑、拆分/删除、手工新增漏检片段与本场商品条目、revision 保存与确认。

验收：刷新可恢复；点击后半段可 Range 播放；两个浏览器页编辑冲突返回 409；合成回放有明显标识；后台失败不能显示“分析成功”。

```text
执行 T5，先使用明确标识的synthetic Fixture进行界面开发，再接真实API。
不要新增设计复杂度，优先让用户完成定位、证据查看、修正和确认。
所有编辑提交expected_revision；保存后新revision不可变。
手工新增片段记录origin=manual；人工边界不必落在ASR句首，保留来源。
人工新增商品只写审核补充目录，不改变运行中输入或原始预测。
风险分展示为审核优先级，未做视觉不能显示音画一致。
测试刷新、跳转视频后半段、两个页面同时编辑，以及服务端失败提示。
```

### T6：正式导出与下载，约 3～4 小时

交付：导出任务和逐片段状态、确认快照冻结、幂等指纹、重新编码、Range 预览/下载、失败项重试。

验收：重复点击得到同一导出；导出时修改新 revision 不改变旧任务；坏片段只影响自己；检查输出内容、时长及音画同步。

```text
执行 T6。导出只接受已确认revision，在创建时冻结所有起止毫秒和编码参数。
每个区间一个MP4，不做混剪或字幕。使用参数数组调用FFmpeg并限制并发。
输出位于本次attempt目录，完成校验后Java引用不可变成片。
验证幂等请求、旧审核版本导出、新revision编辑、部分成功和单项重试。
```

### T7：MVP 集成与首次验收，约 3～5 小时

交付：Compose/本机启动说明、环境模板、真实 30 分钟闭环记录、恢复记录、问题清单。

验收：从启动到上传/分析/审核/导出能按 README 重现；至少一次重启恢复成功；mock 与真实模式明确分开。达到可演示 MVP 后再做展示版。

T3～T7 加上集成返工缓冲后，MVP 累计约 26～40 小时。遇到未解决的问题应保留其证据，不能仅修改 README 宣称完成。

### T8：视觉策略，约 6～10 小时

交付：首中尾基础采样、可见属性响应、风险触发局部采样、帧/token/费用上限、相同预算固定采样基线。

验收：不可见/模糊不误判冲突；无证据不自动改 SKU；预算耗尽会转审核；B/C/D 指标均有真实记录。视觉无增益则保留为实验结论，不反复追求漂亮数字。

```text
执行 T8。增加基础视觉观察，再按规则触发局部加密。
每次请求记录frame_id、实际timestamp、分辨率、输入图像/token、费用与响应。
实现总预算预留及结算，不能只对每段单独限额。
与同模型、同分辨率、相同图像预算的固定采样比较。
报告效果、成本和错误案例，禁止预先写减少调用X%的成果。
```

### T9：MQ、Outbox 与长视频，约 8～12 小时

交付：Outbox 发布、confirm/return、MQ 通知、先 claim 后 ACK、兜底扫描、ASR 持久分块、120 分钟真实运行。

验收：重复发布只有一个有效领取；ACK 后杀 Worker 可恢复；Outbox 发布前后各崩溃一次不丢任务；子任务只重试失败块；长视频资源可控。

```text
执行 T9。保留现有DB调度，将RabbitMQ只作为唤醒通道。
Outbox与READY阶段在同事务写入，发布处理confirm和unroutable return。
Worker拿到执行槽且Java claim提交后才ACK，随后执行。
保留READY和租约扫描，ACK不是计算完成。
长视频ASR按可配置块持久化；所有块完成才进入全局分段。
演练发布器崩溃、重复消息、ACK后崩溃、最后两个子任务并发完成、旧Worker迟到。
```

### T10：评测与作品整理，约 12～20 小时

交付：封存测试运行、消融表、错误分析、费用与耗时报告、SSE 快照恢复、README、演示录像。人工标注通常是这个阶段的主要工作量。

验收：完全按照 [评测与验收](./04-评测与验收.md) 报告原始预测；注明小样本限制、未解决问题和实际硬件。测试集只封存运行，不因为结果不好重新划分。

本阶段与 T8/T9 加上返工，可将整个可信作品投入控制在约 60～90 小时量级；如果素材标注或环境受阻，及时缩小范围。

## 5. 可以并行的部分

T0 契约稳定后，可让一个 AI 负责 Java 协议，另一个负责 Python pipeline，第三个用合成 Fixture 做 UI；共享 contracts 的变更由一个人统一确认和合并。它们必须使用同样的毫秒时间、SKU 状态和错误码。

不能盲目并行的部分：算法范围还未验证就扩建 MQ；双方各自发明接口；多个 AI 同时修改 Schema；没有人工标注就让 AI 自评所有结果为正确。

## 6. 每天的最小交接记录

```text
当前里程碑：
已完成任务与提交：
如何启动/复现：
真实模型运行ID，或明确的mock模式：
通过的验收与证据路径：
当前错误/限制：
本轮实际用量、估算/实际费用：
下一任务与禁止扩大范围项：
```

你需要能解释：一个真实片段如何从 ASR ID 变为时间区间；一个模糊 SKU 为何没有自动归并；Worker 被杀后哪个状态让它恢复；导出为什么不会被后续编辑改变。AI 生成的代码只有经过你运行与理解后，才成为可讲的个人项目。

```text
先阅读 README、01-PRD、02-技术路线、03-AI开发任务书、04-评测与验收及contracts。
当前只执行T0到T2，先做真实视频的命令行技术验证；不要先做前端或MQ。
建立独立LiveCut-AI目录，保留现有项目和简历。
先检查本地FFmpeg、Python、模型API配置，列出缺少的必要输入并继续完成不依赖它们的部分。
最终交付能重跑的命令、商品时间轴JSON、至少3个真实切片、初步质量/费用报告。

```
